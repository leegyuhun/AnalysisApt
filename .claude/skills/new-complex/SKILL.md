# 새 단지 추가 (/new-complex)

입력: **단지명 + 주소** (예: `/new-complex 삼각산아이원 서울 강북구 미아동 1357`). 주소가 부정확하면 먼저
사용자에게 되물어 확정한다 — 동명이인 단지(같은 이름, 다른 지역)가 흔하다.

이 스킬은 자료 수집·판단은 Claude가 그 자리에서 직접 하는 **반자동 워크플로**다. CLAUDE.md에 적혀
있듯 배치도 좌표와 입주민 이야기 요약은 스크립트 산출물이 아니라 손으로(=Claude가 판단해서) 만드는
콘텐츠이고, 이 스킬은 그 판단에 필요한 자료를 브라우저 자동화로 빠르게 모아주는 역할만 한다. 최종
판단(좌표 추정, 리뷰 분류·요약, 문구)은 생략하지 말 것.

## 0. 준비

- `claude-in-chrome` 관련 도구가 로드 안 돼 있으면 한 번에 로드한다:
  `ToolSearch("select:mcp__claude-in-chrome__tabs_context_mcp,mcp__claude-in-chrome__navigate,mcp__claude-in-chrome__computer,mcp__claude-in-chrome__read_page,mcp__claude-in-chrome__get_page_text,mcp__claude-in-chrome__tabs_create_mcp,mcp__claude-in-chrome__tabs_close_mcp,mcp__claude-in-chrome__find")`
- 스크린샷/원문 텍스트는 전부 **세션 스크래치패드 디렉터리**에 저장한다. 저장소 루트에 흘리지 말 것
  (예전에 `byeoksan.png`가 루트에 그대로 남아 untracked로 굴러다닌 전례가 있다).
- 새 탭을 열어 작업하고, 끝나면 `tabs_close_mcp`로 정리한다.
- 다이얼로그(alert/confirm)를 유발할 만한 버튼은 피한다. 호갱노노 리뷰 열람이 로그인을 요구하면
  자동으로 로그인 시도하지 말고, 사용자에게 "브라우저에서 직접 로그인해달라"고 요청한 뒤 대기한다.

## 1. complexNo 확인

```bash
npm run search -- "<단지명>"
```

결과가 여러 개면 주소(동/도로명)로 대조해 정확한 `complexNo`를 고른다. 이미 알고 있으면 생략.

## 2. 네이버지도 캡처 — 위치·주변 랜드마크

1. `map.naver.com`에서 주소로 검색해 단지를 띄운다.
2. 단지 전체 + 주변(정문, 초등학교 방면, 편의점, 어린이집 등 배치도 note에 쓸 만한 지물)이 보이게
   확대/축소한다.
3. 스크린샷을 스크래치패드에 저장한다 (예: `<id>-navermap.png`).
4. 주소 표기(동/로 지번, 도로명)를 여기서 다시 한번 확정해 `apartments.json`의 `address` 필드에 쓴다.

이 캡처는 배치도의 랜드마크 라벨(`LM` 배열)과 카드용 주소를 확정하는 용도다. 동 번호별 좌표의
1차 소스는 다음 단계의 호갱노노 단지 지도 쪽이 보통 더 정확하다 (건물 번호가 찍혀 있음).

## 3. 호갱노노 — 단지 지도(동 배치) 캡처

1. `hogangnono.com`에서 단지명으로 검색해 단지 상세 페이지로 들어간다. 검색 결과가 여러 개면
   주소로 맞는 것을 고른다.
2. 단지 정보 탭에서 **총 세대수 / 총 동수 / 평형별 세대수(전용면적 기준)** 를 읽어 기록한다.
   - 평형별 세대수는 반드시 네이버 부동산 총 세대수(`getComplexDetail`로 이미 얻거나, 매물 스냅샷의
     `detail`)와 합계가 맞는지 교차검증한다. 안 맞으면 note에 그 사실을 명시한다 (samgaksan 페이지
     사례 참고).
3. 단지 지도/동호수 탭이 있으면 펼쳐서 동 번호 배치가 보이는 화면을 스크린샷으로 저장한다
   (`<id>-hogangnono-map.png`). 평형별 색상 구분이 있으면 같이 남긴다.
4. 이 캡처를 보고 각 동의 대략적 (x, y) 좌표와 평형 타입을 **Claude가 직접 추정**해 나중에 `D={}`
   테이블에 넣는다. 라벨이 겹쳐 안 보이는 동(예: samgaksan의 105·106동)은 인접 동을 참고해 추정했다는
   사실을 note/footer에 반드시 밝힌다 — 현장 확인 권장 문구도 넣는다.

## 4. 호갱노노 — 입주민 이야기(리뷰) 전체 수집

1. 리뷰/이야기 탭으로 이동한다. 정렬·필터가 있으면 전체 노출로 맞춘다.
2. `get_page_text` / `read_page`로 화면에 보이는 리뷰를 읽고, 리스트 끝까지 스크롤하며 반복한다.
   무한 스크롤이면 더 이상 새 항목이 안 늘어날 때까지 진행한다.
3. 원문을 스크래치패드에 통으로 저장해둔다 (`<id>-reviews-raw.txt`). 이후 요약 근거로 재확인할 때 쓴다.
4. 리뷰 옆에 평형/거주 상태(입주민/전세/월세 등) 태그가 있으면 같이 남긴다 — 인테리어 비용 언급이나
   불만 사항이 특정 평형에 몰리는지 구분할 때 필요하다.

**원문 리뷰를 페이지에 그대로 옮기지 않는다.** 기존 페이지처럼 다음 카테고리로 직접 분류·요약한다:

- 단지 기본값(세대수/동수/평형/입주년월 등 사실 확인)
- 무엇이 가장 많이 언급되나 (빈도)
- 장점
- 단점
- 인테리어 — 확인된 것만 (비용 감각, 시스템에어컨/세탁실 등 구조적으로 반복 언급되는 것)
- 형님용 한 줄 판단 (bottom line)

톤·분량은 `byeoksan-map.html`, `samgaksan-map.html`의 해당 섹션을 그대로 기준으로 삼는다.

## 5. 페이지 작성

1. `samgaksan-map.html` (가장 최근 예시)을 템플릿으로 복사해 `<id>-map.html`로 만든다.
2. 다음을 교체한다:
   - `<title>`, 히어로 문구, `counts`
   - 팔레트 변수(`--pine`, `--clay`, `--gold` 등) — 단지마다 다른 accent를 쓰는 게 관례
   - `T`(평형 타입), `D`(동 좌표/평형/층수), `LM`(랜드마크) — 2·3단계 캡처 기반
   - 평형별 동 목록 테이블은 스크립트가 `D`/`T`에서 자동 생성하므로 손댈 필요 없음
   - 입주민 이야기 각 섹션 본문 (4단계 요약)
   - 하단 `AptArticles.mount` 의 `complexNo`, `pyeongAlias`
   - footer의 출처 문구(네이버 부동산 complexNo, 호갱노노 등) — 근사치/추정 부분은 반드시 명시
3. `README.md`의 "단지 추가하기" 절차대로 공용 스타일 링크, 복귀 바(`topbar`), `#articles`가 들어있는지
   다시 확인한다.

## 6. 등록 및 데이터 수집

1. `data/apartments.json`에 항목 추가 (`id`, `name`, `file`, `complexNo`, `region`, `address`, `built`,
   `households`, `buildings`, `accent`, `tags`, `summary`, `highlights`).
2. 매물 스냅샷 수집:

   ```bash
   npm run scrape -- --complex <complexNo>
   ```

3. `npm run serve`로 띄워 카드 노출, 배치도 탭 렌더링, 매물 탭 로딩을 직접 확인한다.

## 7. 마무리

- 스크래치패드에 남긴 캡처/원문 리뷰는 저장소에 커밋하지 않는다 (참고용, 세션이 끝나면 사라져도 무방).
- 변경분을 요약해 사용자에게 보여주고, **커밋은 사용자가 원할 때** 한다 (자동으로 커밋·푸시하지 않음).
- 좌표·세대수 등에 추정치가 섞였으면 마무리 보고에서 어떤 부분이 추정인지 다시 한번 짚어준다.
